# Legacy test gaps, group A: the binding permission check and reads failing once

The legacy offline tests (`scripts/integration/*.test.ts`, commit `17c1f1f`) proved on in-memory stores that (1) a right taken away between the quick permission check and the writing transaction (or after the form was shown) is refused by the check inside the transaction, with nothing written, and (2) a read that fails once comes out as that same error — never "no right", "nothing stored" or zeros — writes nothing, and the retry succeeds. The new tests prove the same on the real SQL Server through the test seam `DbOptions.Interceptor` (see `docs/DEVELOPMENT.md`, "Failure injection").

Files: `I/` = `tests/Insurance.Integration.Tests/FailureInjection/`, `W/` = `tests/Insurance.Web.Tests/FailureInjection/`. A case written `(quick|binding) × (own decisions|memberships|group grants)` is one theory with a row per combination. Each "between the quick check and the transaction" test and each binding-read test was run against the code with the binding check removed (negative control): every one of them failed (16 + 8 tests), the quick-check ones passed, as expected.

## Defects found and fixed

- **D1** — `PermissionPanel.ChangeAsync`: a group name taken by another admin between the look-up and the insert (or rename) threw the unique index's error; legacy `createGroup` / `renameGroup` answered it as "duplicate-name". Now the rolled-back change is answered `duplicate-name`, nothing written. Test fails on the old code (SqlException 2601).
- **D2** — `Pages/Claims/Claim.cshtml`: a pay form sent after the permission was taken away got the page back without the form and without the refusal (the message was rendered only inside the form); legacy's form kept showing the action's Georgian answer. Now the refusal is shown when the form is no longer offered. Test fails on the old code. The existing `ClaimPagesTests.A_viewer_posting_the_payment_reserve_or_registration_forms_directly_is_refused_and_nothing_is_written` asserted the message was not shown on a viewer's direct post; it now asserts that it is (the same page path).

## Open questions (technical, for the reviewer; no business rule involved)

- **Q1** — closed: fd panel lists now turn any error of a list read into "could not be read", as legacy `readPendingQueue` did (only a cancelled request, OperationCanceledException, is let through); before, only SqlException and InvalidOperationException were caught and any other exception failed the page (`FdPanel.ReadPendingQueueAsync`; test above).
